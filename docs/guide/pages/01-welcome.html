The story we will follow

Priya's team at Acme Shop has an assistant called Sidekick. Colleagues ask it questions in plain English and it writes the SQL for the shop's database. Last week they shipped version 2. Since then people say the revenue questions come back wrong. Was version 2 worse than version 1? Nobody can say: each person tried a few questions by hand and remembers something different.

By the end of this guide Sidekick has a test set, two measured versions, a clear winner, and a build that stops anyone shipping a worse one.

Priya, Acme Shop and Sidekick are made up, and the numbers are illustrative. The behaviour is real.

What nl2sql_evalkit does

You hand it a function. It does the repetitive, error-prone part of testing for you.

Your assistantnl2sql_evalkit calls your function once per test question, in order, like a real user.
→
Checks and gradingThe SQL is read, not run: does it parse, is it read-only, does it use the right tables, columns and joins? An AI judge then scores it.
→
VersionsEvery run is saved as a version, so you can see what improved and what broke.
→
The decisionA recommendation says which version to ship, and why.
Static checks only

No database connection is needed and no query is ever executed. That keeps a run safe and quick; the price is that the judge reads the SQL instead of comparing the rows it would return.

Three words you will meet

Test caseA question and what a good reply looks likeThe SQL you expect, optionally the tables and columns it should use, and what kind of reply it is: an answer, a question back, or a refusal.
VersionOne run of your test casesYou name it (1, v2, new-prompt). Versions are what you compare.
JudgeThe graderAn AI model by default. It can also be your own function, or your own rubric.

Your code stays yours

Evaluation lives in a small entry file next to your pipeline. Your production app keeps running exactly as before, and the optional recording calls (step(), note()) do nothing outside an evaluation.
