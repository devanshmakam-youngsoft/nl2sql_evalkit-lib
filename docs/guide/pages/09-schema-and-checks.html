The checks

The SQL is parsed in the dialect you gave to serve(dialect=…) and read. Nothing is run and no database is needed. The result of each check is shown under the question and counted in the “where answers fail” table of the version.

CheckIt passes when…
Parsesthe SQL is valid in your dialect (postgres, mysql, tsql or sqlite)
Read-onlyit is one single query. Anything that writes or changes things fails: INSERT, UPDATE, DELETE, DROP, SELECT … INTO, a second statement, and risky functions such as pg_sleep or xp_cmdshell
Expected tablesevery table listed in expected_tables appears in the query
Expected columnsevery column listed in expected_columns appears. Write orders.amount or just amount. SELECT * gets the benefit of the doubt, since it cannot be told apart
Joinsthe query joins on the same pairs of columns as your expected_sql. Aliases do not matter; extra joins and missing joins are both listed

A check only runs when it has something to compare with. No expected_tables means no table check, and no expected_sql means no join check, and neither counts as a failure.

What stops a reply early

Some failures are certain, so the judge is not asked and the SQL score is 0 with the reason and a suggestion:

  • an answer case that returned no SQL;
  • SQL that does not parse in your dialect;
  • SQL that is not read-only;
  • a clarify or refuse case that returned any SQL at all.

Everything else goes to the judge.

What counts as SQL

A reply is SQL when it sits inside a ```sql fence, or when it starts like a statement: SELECT, WITH name AS (, INSERT, DELETE, DROP and so on. Any other reply is read as a message. A query whose first word is misspelled, such as SELEC, is therefore read as a message and fails as “no SQL”.

Two scores

SQL score0 to 10, from the judgeThe judge reads the question, your expected SQL (if any), the reply and what the checks found. It does not need the same text: a different query that answers the question can score well. It gives a reason and a suggestion for each question.
Tables and columns0 to 10, from the checksThe share of the expected tables used and the share of the expected columns used, averaged when you gave both. No judge, so it never varies between runs.

Examples: a query that uses 2 of 2 expected tables and 3 of 4 expected columns scores 9 (the average of 100% and 75%, rounded). A reply with no usable SQL scores 0 when something was expected. Nothing expected, or a clarify or refuse case, and there is no tables-and-columns score for that question.

The two scores are combined for the recommendation with sql_weight (0.6) and schema_weight (0.4). Set schema_weight=0 to look at the SQL score only. Versions and the recommendation shows how.

What a test case holds

FieldMeaning
questionwhat the user asks
expected_sqla query that answers it correctly: the judge's reference and the source of the join check
expected_tablesthe tables the query should use, separated by commas
expected_columnsthe columns it should use, separated by commas
typeanswer, clarify or refuse

An answer case needs at least one of the three expected_ fields, otherwise there is nothing to compare with. The more you give, the sharper the checks.

The limit of reading SQL

Because nothing is run, the checks cannot know whether two different queries return the same rows. The tables, columns and joins are strong hints, and the judge weighs the rest, but a query can pass every check and still be wrong. Judge scores can also move a little between runs; the checks never do.
