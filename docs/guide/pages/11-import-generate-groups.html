Importing

  • You see what will be added, updated or skipped before anything is saved, with the row number and reason for every row that cannot be used.
  • Only the question column is required, plus one of expected_sql, expected_tables or expected_columns on every answer row. Common header names (user_query, gold_sql, tables, tags…) are recognised, and you can point any column at the right field.
  • A type other than answer, clarify or refuse is reported as a problem on that row.
  • Safe to repeat: importing the same file twice changes nothing; an edited expected SQL becomes a new version of the existing case.
  • Rows that could not be imported can be downloaded with the reason next to each, fixed, and imported again.
  • Your own column names everywhere? column_map={"user_query": "question", "gold_query": "expected_sql"} in serve().

Generating from a schema

Test Cases → Generate from a schema writes questions from the tables, columns and keys in your .sql, .ddl or .txt files (up to 5 files of 10 MB). Nothing is connected or run: the files are read for their CREATE TABLE statements, and a dump that also holds INSERT data is fine. The files are read in the dialect you set with serve(dialect=...). By default it writes three questions in each of seven categories:

CategoryWhat it isType
SimpleOne table: filter, sort or list.answer
JoinsTwo or three tables that are linked by a foreign key, joined on those keys.answer
AggregationsCounts, sums, averages, minimums or maximums, often grouped.answer
SubqueriesNeeds a subquery or a WITH.answer
Follow-upsA short conversation (3 turns by default). Each follow-up depends on the earlier answer and cannot be understood alone.answer
VagueA question that cannot be answered without asking what is meant. It carries a note saying why it is unclear.clarify
UnsafeA request to change or destroy data. It carries a note saying what is wrong with it.refuse
  • Every query is checked before you see it. It must parse in your dialect, be one read-only SELECT, use only tables and columns that exist, and match its category (a join question must join on the declared keys). A rejected one is rewritten with the reason, up to three times.
  • Expected tables and columns are read from the SQL, not guessed by the model. Columns used only to join are left out.
  • Questions use everyday words: no “table”, “column” or “SQL”, except in the unsafe ones. Near-duplicates are rejected.
  • Review, then add. Questions are saved while they are being written, so closing the browser loses nothing. You can edit a question or its SQL (new SQL is checked the same way) or remove any of them. Nothing is added until you press Add; each category becomes its own group.
  • Nothing of the upload is kept, only the questions and expected SQL.
  • The names of your tables and columns go to the model you set with generator_model (the judge model by default). A local ollama/… model keeps them on your machine.
Tip

Without declared foreign keys the generator can only guess links from names like customer_id, so join questions are fewer and the join check has less to compare. Add the keys to the DDL if you can. A schema with a single table gets no join questions.

Groups

A group is a label. A case can carry any number of labels, and you add or remove them from the Test Cases page. Use them to run a slice (“only Joins”) and to see scores per slice on the version page. When you run several groups, a case in two of them runs once.

Follow-up questions need the turns before them, so by default a run also includes the earlier turns of every case you picked. The Execute dialog shows exactly how many cases will run, and lets you turn that off.

Deleting: a test case is removed for good (past versions keep their own copy of the question and expected SQL, marked “Test case deleted”). A group is only hidden and can be restored. To keep a case but skip it in runs, mark it inactive.
