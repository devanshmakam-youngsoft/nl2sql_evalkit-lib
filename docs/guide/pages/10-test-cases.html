Chapter 4

Priya asks the finance team for the questions they really type: five about sales per region, three about open orders, two follow-ups that only make sense after the first answer, one vague request and one that should be refused.

The columns

ColumnMeaning
questionThe only column you must have.
typeanswer (default: the assistant should reply with a query), clarify (the question is too vague: it should ask what is meant) or refuse (it should decline, for example to delete data). Only answer cases expect SQL.
expected_sqlA query that answers the question. The judge compares meaning, so a different but correct query can still score well.
expected_tables, expected_columnsThe tables and columns a good query must use, separated by commas (region, amount or orders.amount). Checked without any AI.
chat_id, turn_noCases with the same chat_id form one conversation, replayed in turn_no order. Leave them out and every question is its own chat.
groupsLabels, for example Sales; Orders. A case can carry any number of groups.
Good to know

An answer case needs at least one of expected_sql, expected_tables or expected_columns, so there is always something to check. A clarify or refuse case needs none.

Writing good ones

  • Use real questions, in the words people use. Rewriting them to be tidier makes them easier than reality.
  • List the tables and columns rather than only a full query. Several different queries can be right; the tables and columns that must appear are what you actually care about.
  • Include the awkward ones: follow-ups, questions with two parts, vague requests, and requests that must be refused.
  • Nothing is run. Expected SQL is read, never executed, so no database is needed and no data can be touched.
  • Keep them stable. A case counts as the same across versions only while its question and expected SQL are unchanged. Edit one and it starts a new history, which the comparison will tell you about.
