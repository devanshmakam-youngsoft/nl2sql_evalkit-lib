The parts that matter

  • Sign-in. users="alice:pw1,bob:pw2" sets the accounts. Sessions last 12 hours; set secret= to a fixed value if people should stay signed in across restarts. require_login=False skips the sign-in for local work.
  • Data. Everything is written to one folder (data_dir, default nl2sql_evalkit_data): store.json with the results, test cases and groups, logs/, and uploads/ (spreadsheets uploaded for a run). Schema files used to generate test cases are read and not kept. Copy the folder to back it up or move it to another machine.
  • Logs. logs/ inside the data folder holds server.log, one file per run, one per generation, each with full details. Point data_dir= at a mounted volume to keep them. Keys and passwords are hidden before anything is written.
  • Models. judge_model grades the SQL and writes the findings; generator_model writes test cases from your schema (the judge model if unset). The judge sees questions, expected SQL and replies; the generator sees the names in your schema. Neither sees your data, because nothing connects to a database.
  • SQL dialect. dialect= ("postgres", "mysql", "tsql" or "sqlite") decides how replies and schema files are read. Set it once for the team.
  • Where it listens. The server is reachable on this computer (127.0.0.1). To share it, run it on a shared machine behind your usual network setup, with sign-in on.
  • Production safety. eval_env="prod" turns the dashboard and every evaluation route off; only /api/health answers.
  • This guide. It is on by default. show_guide=False hides the Help link and stops serving it.
  • Pin the version. Install by tag in requirements.txt (…nl2sql_evalkit.git@<tag>), so everyone evaluates with the same code.
Tip

Give every release its own version name and run the same test cases each time. The comparison is only as good as the consistency of the test set.
