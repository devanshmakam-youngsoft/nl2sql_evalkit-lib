The scores

You seeIt means
SQL score (0–10)The AI judge reads the question, the expected SQL and the reply, and says whether the query would answer the question, with a reason and a suggestion. A reply that fails a basic check is scored 0 without asking the judge (see below).
Tables and columns (0–10)Worked out without AI: the share of the expected tables, and of the expected columns, that the query uses. Left out when the test case expects none.
Schema lookup (0–10)Only when your assistant records which tables and columns it looked at (see steps). Worked out without AI: the share of the expected tables and columns that were in what it looked at. A low score means the lookup missed something the question needed, whatever the SQL did. It is not part of the overall score.
Response time and the step barFrom question to final reply, and how that time splits across your steps.
Score tiersHow many questions were strong (8–10), fair (5–7) or weak (0–4).
Where answers failHow many replies failed each check. See below.

The checks

The SQL is read, never run. Each reply goes through these checks first:

CheckWhat fails it
No SQLAn answer question with no query in the reply. A reply counts as SQL if it is in a code fence or starts with SELECT, WITH, INSERT, DROP and the like.
ParsesThe query is not valid in your dialect.
Read-onlyMore than one statement, anything that changes data or the schema (INSERT, UPDATE, DELETE, DROP…), or a risky function such as pg_sleep.
Expected tables / columnsAn expected table or column does not appear in the query. A SELECT * gets the benefit of the doubt on columns.
JoinsThe query joins on different column pairs from the expected SQL.

No SQL, SQL that does not parse and SQL that is not read-only score 0 and the judge is not asked. For clarify and refuse questions the rule is turned round: any SQL in the reply scores 0, and a reply with only words goes to the judge, which checks it really asks or declines.

Where answers fail

The version page and the dashboard show, for each check, how many replies failed it out of the questions that should be answered (and, for declines, how many wrote SQL when they should not have). When the assistant records its schema, a row also counts the questions where what it looked at lacked an expected table or column. On the dashboard it compares your latest versions side by side, with an arrow for the change since the run before, so you can see that v3 fixed the joins but broke the columns. Lower is better.

Watch-outs and suggestions

At the end of each run the judge model writes plain-language findings: each thing to look at, paired with the next step to try. They name the group or question and use the numbers as evidence, rather than repeating the headline scores. If the model cannot be reached, a plain summary built from the checks is shown instead. Change what the model looks for with summary_prompt (Your judge).

One question at a time

Click any row to open that question: the reply, the SQL read from it, the expected SQL, the schema the assistant looked at (when recorded) with each expected table and column marked found or missing, each check with what it found, the judge’s reason and suggestion, the time per step, and your notes. This is where wrong queries get explained.

When the SQL is wrong and a schema was recorded, the judge also says why: the schema lookup missed something (fix what the assistant looks up), the SQL went wrong with the schema it had (fix how it writes), or both. It is shown as the likely cause, so you do not start by changing the wrong part.

  • Filter by type, group or score tier, and sort by score or time.
  • A question whose test case has been deleted since is marked, and keeps its own copy of the text.
  • Download an Excel report from the version page: a summary sheet, and one row per question with the checks.
  • Scores from the AI judge can differ a little between runs of the same version. The checks never do. Read a difference of a point or so as noise, and a drop in a check count as real.

Problems during the run

If something went wrong, the version page lists it in plain words, with Show technical details for the error and Download log for the full story. The same problem on many questions is listed once with a count. While a run is going you see a live count.

  • A failing assistant function never stops a run: that question is marked failed, the reason is recorded, and the run goes on.
  • Logs are in the logs/ folder of your data folder (nl2sql_evalkit_data/ by default): server.log, one file per run, one per generation. Keys and passwords are hidden before anything is written.
Tip

Read Problems during this run before the scores. A run where half the questions failed has misleading averages.
